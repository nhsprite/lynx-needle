# lynx-needle

A [Lynx](https://github.com/lynx-family/lynx) weak NAPI addon that embeds
[Cactus Needle 2](https://github.com/cactus-compute/needle) — a 45M-parameter,
2-bit tool-calling model — into Lynx pages on Android and iOS. The whole
engine (weights included) is one ~14MB static library; inference needs ~28MB
RAM and no network.

```
Lynx page JS ──▶ needle NAPI addon (this repo) ──▶ libneedle.a (engine, weights baked in)
```

## What the model does

Tool calling and structured extraction. You declare JSON-Schema tools, the
model returns structured calls (`{name, arguments}`) with a calibrated
confidence score. A byte-level grammar compiled from your schemas constrains
every output token. With more than 5 tools declared, a retrieval head renders
only the top-5 per turn. Context is a 256-token sliding window (tools pinned),
so memory stays bounded regardless of conversation length.

## Prerequisites: NAPI requires a source-built Lynx runtime

The Lynx NAPI addon flow (`requireNodeAddon` / `__lynx_node_addon_exports__`)
is an **experimental capability** and is **not compiled into the published SDK
binaries**. We verified that the `liblynx.so` shipped by every Maven artifact
(`org.lynxsdk.lynx:lynx` 3.9.1, 3.9.1-dev, 4.0.1, 4.0.0 / 4.1.0 nightlies,
plain and `-dev`) was built with `enable_napi_binding=false` —
`RuntimeLifecycleListener.onRuntimeAttach` never fires, so no `napi_env` is
ever handed to the host and addons cannot load.

To run a page that uses this addon end-to-end, the host app must embed a Lynx
runtime **built from source with NAPI enabled**. The source-tree default is
also `false` ([`core/napi.gni`](https://github.com/lynx-family/lynx/blob/develop/core/napi.gni));
what makes it work in LynxExplorer is that the Explorer build passes
`enable_napi_binding=true enable_lepusng_worklet=true` as gn args (Android:
[`explorer/android/gradle.properties`](https://github.com/lynx-family/lynx/blob/develop/explorer/android/gradle.properties);
iOS: the podspec generation script passes the same args). A source build for a
custom host must pass the same args. See the Lynx
[`lynx-napi-addon` doc](https://github.com/lynx-family/lynx/blob/develop/explorer/android/lynx-napi-addon.md)
for background.

On iOS the published pods are also not sufficient, for a different reason:
the `Lynx` podspec does define `ENABLE_NAPI_BINDING=1`, but (a) the PrimJS and
LynxWeakNodeAPI pods ship colliding public `js_native_api*.h` headers (the
example's Podfile works around this with forwarding headers) and (b) the
`Lynx` pod's NAPI sources reference `third_party/napi/include/*` headers that
are not packaged in the pod. So a working iOS NAPI build likewise requires
building Lynx from source (as LynxExplorer does).

The SDKs and examples in this repo are correct against that capability and
work as soon as the host's Lynx runtime includes it; against the published
Maven/CocoaPods binaries the frontend API simply reports the addon as
unavailable (`loadNeedle()` returns `null`).

## Client integration

### Android (`android/`)

The SDK is a Gradle library module that bundles everything native: the
`LynxNodeAPI` bridge module, the `lynx_napi_addon_loader` .so (built from
`cpp/LynxNodeAPI.cc`), `libneedle.so` and `libnapi_adapter.so` (both ABIs).

```gradle
// settings.gradle
include ':lynx-needle-sdk'
project(':lynx-needle-sdk').projectDir = new File('<path-to-repo>/android')

// app/build.gradle
dependencies { implementation project(':lynx-needle-sdk') }
```

Two calls in your app:

```java
// 1. Once, after LynxEnv.init (e.g. in Application.onCreate):
LynxNeedle.registerModule();          // registers "LynxNodeAPI" globally

// 2. Per LynxView, after LynxViewBuilder.build():
LynxNeedle.attach(lynxView);          // binds the runtime's napi_env
```

Page JS can then `requireNodeAddon("needle")`. First-time setup of the native
artifacts:

```bash
npm install && npm run fetch-engine   # engine static libs
npm run build:android                 # -> android/src/main/jniLibs/<abi>/{libneedle,libnapi_adapter}.so
```

### iOS (`ios/`)

```ruby
# Podfile
pod 'LynxWeakNodeAPI', :subspecs => ['core', 'primjs_bridge']
pod 'needle', :path => '<path-to-repo>/ios'
```

```objc
// AppDelegate.mm — once, at startup:
#include "addon_use.h"   // keeps the addon's static registration alive
InstallPrimJSWeakNodeApiBridge();   // see examples/ios-host for the snippet

// Per LynxView — one background runtime, module + listener wired by a token:
self.moduleToken = [NSObject new];
self.runtime = [[LynxBackgroundRuntime alloc] initWithOptions:options];
[self.runtime addRuntimeLifecycleListener:
    [[LynxNodeAPILifecycleListener alloc] initWithToken:self.moduleToken]];
[self.runtime registerModule:[LynxNodeAPIModule class] param:self.moduleToken];
// then: builder.lynxBackgroundRuntime = self.runtime;
```

Produce the pod artifacts with:

```bash
npm run build:ios        # -> build/ios-{device,sim}/out/libneedle.a
npm run package:darwin    # -> ios/{needle.xcframework, needle.podspec, ...}
```

## Frontend usage (npm package)

```bash
npm install lynx-needle        # or: "lynx-needle": "file:<path-to-repo>"
```

For the local `file:` form, build the package first (`npm run build` at the
repo root) — `lib/` is generated by tsc and not committed.

```js
import { loadNeedle } from 'lynx-needle'

const needle = await loadNeedle()   // null when the host has no addon loader
if (!needle) { /* show setup instructions */ }

// 1. Declare tools and start a session.
needle.init('You control a smart home.', [
  {
    name: 'set_lights',
    description: "Turn a room's lights on or off and set brightness",
    parameters: {
      type: 'object',
      properties: {
        room: { type: 'string' },
        on: { type: 'boolean' },
        brightness: { type: 'integer', minimum: 0, maximum: 100 },
      },
      required: ['room', 'on'],
    },
  },
])

// 2. Agent loop: the model decides calls, your handlers execute them.
const result = await needle.run('dim the living room to 30', {
  set_lights: ({ room, on, brightness }) => ({ room, on, brightness, applied: true }),
})
// result.function_calls / result.results / result.confidence / result.peak_ram_mb

// 3. One-shot structured extraction.
const invoice = await needle.extract('Invoice from Acme Corp, $1,200.00, due 2026-09-01', {
  name: 'Invoice',
  parameters: {
    type: 'object',
    properties: { vendor: { type: 'string' }, total: { type: 'number' }, due_date: { type: 'string' } },
    required: ['vendor', 'total', 'due_date'],
  },
})
```

API summary (full types in `src/needle.ts`):

- `loadNeedle(timeoutMs?) → Promise<NeedleAgent | null>` — asks the host
  loader for the addon and waits for the exports object (the bridge call is
  async fire-and-forget; `NativeModules` is a bundle-scope identifier injected
  by Lynx, not a real global).
- `init(system, tools, toolIndexPath?)` — (re)start the session.
- `complete(input, maxNewTokens?) → Promise<NeedleResponse>` — raw inference,
  off the JS thread.
- `run(query, handlers, {maxSteps, maxNewTokens}) → Promise<NeedleRunResult>`
  — the agent loop (adds `results`).
- `extract(text, schema, {system, maxNewTokens})` — one-shot extraction.
- `reset()` — rewind the conversation, keep tools.
- `load(cactPath)` — bind LoRA-tuned weights (one-way!).
- `engineVersion()` — e.g. `"2.0.3"`.

`response` envelope:

```json
{
  "type": "call",
  "function_calls": [{"name": "set_lights", "arguments": {"room": "living room", "on": true, "brightness": 30}}],
  "confidence": 0.92,
  "reasoning": "...",
  "prefill_tps": 668.2, "decode_tps": 161.6, "peak_ram_mb": 27.7
}
```

`type === "call"` with an empty `function_calls` means the model refused an
off-topic input; `"respond"` means the loop finished. There is no free-text
fallback by design.

## Run the demos

### Android: `examples/android-host` × `examples/lynx-needle-demo`

```bash
# 1. Repo root: build the addon into android/src/main/jniLibs (once per addon change)
npm install && npm run fetch-engine && npm run build:android

# 2. Frontend demo dev server (prints the bundle URL / QR)
npm run build   # the demo consumes lib/ via a file: dependency on the repo root
cd examples/lynx-needle-demo && npm install && npm run dev   # e.g. :3000/main.lynx.bundle

# 3. Host app (JDK 17 + Android SDK)
cd ../../examples/android-host
./gradlew :app:assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
# Open "Needle Host", enter the bundle URL, GO.
```

Note the runtime prerequisite above: with the stock Maven `liblynx.so` the
page renders but reports "addon not available". Swap in a source-built
`liblynx.so` (jniLibs, `pickFirst` already handles the conflict) to see the
full flow.

```bash

npm run build:ios && npm run package:darwin

# 2. Frontend demo dev server (same as above)

# 3. Host app (requires CocoaPods; generates the Xcode project on first run)

ruby generate-project.rb      # one-time, needs the xcodeproj gem (bundled with CocoaPods)

```

## Build the addon from source

Prerequisites: Node ≥ 22, CMake, `npm install`. Engine binaries are pinned to
needle engine **2.0.3** and fetched from Hugging Face:

```bash
npm run fetch-engine    # needle.h + libneedle.a for android/ios (+ macos for local dev)
```

### Android (arm64-v8a, armeabi-v7a)

```bash
npm run build:android   # ANDROID_NDK auto-detected from $ANDROID_HOME/ndk
# → android/src/main/jniLibs/<abi>/{libneedle,libnapi_adapter}.so
```

Note: `armeabi-v7a` builds compile `cpp/shim_hash_memory.cc` — the prebuilt
32-bit engine references `std::__ndk1::__hash_memory`, which modern NDKs no
longer export; the shim is the canonical libc++ murmur2 implementation.

### iOS (arm64 device + simulator)

```bash
npm run build:ios
# → build/ios-{device,sim}/out/libneedle.a (merged with engine)
npm run package:darwin
# → ios/{needle.xcframework, needle.podspec, include/addon_use.h}
```

### macOS (local development / Lynx embedder)

```bash
npm run build:macos     # → build/macos/out/libneedle.a
```

## How it works

- `cpp/addon.cc` — NAPI bindings over the engine's 4-function C ABI
  (`needle_init` / `needle_complete` / `needle_reset` / `needle_load`, see
  `third_party/needle/include/needle.h`). `complete` runs on a
  `Napi::AsyncWorker` so inference never blocks the JS thread; a process-wide
  mutex serializes all engine calls because the engine is single-session and
  not thread-safe. The 64KB output buffer grows to 1MiB and retries once if
  the engine reports failure.
- `cpp/LynxNodeAPI.{h,cc}` — the platform-independent addon loader
  (vendored from `lynx-family/lynx` `explorer/cpp`, develop branch): on
  Android it `dlopen`s `lib<name>.so`, on Darwin platforms it resolves the
  statically registered module, then publishes the addon exports on
  `globalThis.__lynx_node_addon_exports__.<name>`.
- `android/` + `ios/` — the platform glue: a `LynxNodeAPI` bridge module
  plus the runtime-lifecycle plumbing that binds each JS runtime's `napi_env`.
- `CMakeLists.txt` — links the per-platform `libneedle.a`; on Darwin the
  engine archive is `libtool`-merged into the addon archive so each
  xcframework slice is self-contained.
- `tools/fetch-engine.sh` — pins and downloads engine artifacts.

## Known limitations (engine-inherent)

- **Single global session.** Multiple agents share one conversation state;
  re-`init` to switch toolsets, or run separate processes.
- **256-token sliding window.** Long conversations silently drop old context
  (tools stay pinned).
- **Tuned weights are one-way.** After `load()`, the base model cannot be
  restored in-process, and `confidence` becomes uncalibrated (`null`).
- **No streaming.** The ABI returns the whole response at once.
- The `requireNodeAddon` / `__lynx_node_addon_exports__` flow is marked
  **experimental** by Lynx; production hosts should wrap addon loading behind
  their own module registration and constrain load paths.
